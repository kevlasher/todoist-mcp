# Behavior Inventory — Todoist MCP Server

Generated by reading every file in `src/`, `src/tools/`, and `test/` as of the
current repository state. Each entry is one observable behavior with a test
status marker. This is an inventory, not an assessment — behaviors that look
accidental, inconsistent, or undesirable are included alongside intended ones.

**Cross-cutting fact that affects how to read this document:** of the 7 read
tools and 9 write tools registered, only `find-projects` and `find-tasks` are
ever actually invoked (via `callTool`) in the test suite (`test/mcp-e2e.test.js`).
`find-tasks-by-date`, `find-sections`, `find-labels`, `find-comments`,
`get-overview`, and all 9 write tools are checked only for *registration/
presence* (`test/registration.test.js`), never for handler behavior. Any
handler-specific logic in those tools is [UNTESTED] unless it is covered
indirectly through a lower-level unit test (e.g. `client.js`, `sanitize.js`).

---

## 1. Configuration (`src/config.js`)

- Read-only mode is the default; writes are enabled only when `TODOIST_READONLY`
  is the exact string `"false"`. Unset, empty, `"true"`, `"0"`, `"FALSE"`, `"no"`,
  or any other value all resolve to read-only.
  [TESTED] `test/config.test.js` — `'read-only default is fail-safe: unset => read-only'`,
  `'only the exact string "false" enables writes'`.
- Numeric config values (`TODOIST_MAX_OUTPUT_CHARS`, `TODOIST_MAX_FIELD_CHARS`,
  `TODOIST_MAX_ITEMS`) fall back to their default when the env var is unset.
  [TESTED] `test/config.test.js` — `'loadConfig parses caps with sane defaults'`.
- Numeric config values fall back to their default when the env var is present
  but not parseable as an integer (e.g. `"not-a-number"`).
  [TESTED] `test/config.test.js` — `'loadConfig parses caps with sane defaults'`.
- Numeric config values fall back to their default when the env var is an
  **empty string** specifically (as opposed to unset or non-numeric).
  [UNTESTED] — same code branch as the above two, but no test sets `""` explicitly.
- Numeric config values ≤ 0 (e.g. `"0"`, `"-5"`) are rejected and fall back to
  the default, per `n <= 0` check in `intFromEnv`.
  [UNTESTED]
- The API token can come from `TODOIST_API_KEY` directly, and this takes
  priority over `TODOIST_API_KEY_FILE` when both are set.
  [TESTED] `test/config.test.js` — `'direct TODOIST_API_KEY takes priority over the file'`.
- The API token can be sourced from a file path in `TODOIST_API_KEY_FILE`;
  file contents are trimmed before use.
  [TESTED] `test/config.test.js` — `'token can be sourced from a file via TODOIST_API_KEY_FILE'`.
- If `TODOIST_API_KEY_FILE` points to a file that cannot be read, `loadConfig`
  throws a fixed generic message (`"TODOIST_API_KEY_FILE could not be read."`)
  that does not include the underlying OS error text or path contents.
  [TESTED] `test/config.test.js` — `'an unreadable key file surfaces a config error without leaking the path contents'`.
- If the resolved file contents are empty or whitespace-only after trimming,
  `resolveToken` returns `''`, and `loadConfig` then throws the "not set" error
  (file is silently treated as if it doesn't exist).
  [UNTESTED]
- If `TODOIST_API_KEY` is set but is an empty/whitespace-only string, it is
  treated as not-set and the code falls through to check `TODOIST_API_KEY_FILE`.
  [UNTESTED]
- With no usable token from either source, `loadConfig` throws
  `'TODOIST_API_KEY is not set...'` and never echoes any credential value.
  [TESTED] `test/config.test.js` — `'loadConfig throws without a token and never echoes it'`.
- Default caps when unset: `maxOutputChars=50000`, `maxFieldChars=2000`,
  `maxItems=200`.
  [TESTED] `test/config.test.js` — `'loadConfig parses caps with sane defaults'`.
- `loadConfig` accepts an injectable `readFileSync` dependency for testing; the
  default production path uses Node's real `fs.readFileSync` and is never
  exercised by any test (all config tests inject a fake).
  [UNTESTED]

## 2. Redaction (`src/redact.js`)

- `registerSecret` silently ignores non-string values and strings shorter than
  4 characters (they are never added to the scrub set).
  [UNTESTED]
- `redact()` replaces **every** occurrence of **every** registered secret in a
  string with `[REDACTED]`.
  [TESTED] `test/redact.test.js` — `'registered token is scrubbed from arbitrary strings'`.
- `redact()` coerces non-string input via `String(input)` before scrubbing.
  [UNTESTED] — no test calls `redact()` with a non-string argument directly.
- `redact()` redacts `Bearer <token>`-shaped substrings even if the token was
  never registered.
  [TESTED] `test/redact.test.js` — `'Bearer material is redacted even if not registered'`.
- `redact()` redacts `authorization: <value>`-shaped substrings regardless of
  quoting/case, even if unregistered.
  [TESTED] `test/redact.test.js` — `'authorization header value is redacted regardless of format'`.
- `redactError()` returns `{message, stack}` for `Error` instances, redacting
  both fields; `stack` is only included if `err.stack` is truthy.
  [TESTED] (message+stack-present case only) `test/redact.test.js` — `'redactError scrubs message and stack'`.
  The branch where `err.stack` is falsy is [UNTESTED].
- `redactError()` returns `{message: redact(err)}` for non-`Error` inputs.
  [UNTESTED]
- Registered secrets accumulate in a module-level `Set` for the lifetime of the
  process; there is no `unregisterSecret` — once a token is registered it is
  scrubbed forever, and nothing bounds the set's size if many distinct secrets
  were ever registered.
  [UNTESTED] (no test asserts unregistration, isolation between calls, or
  memory bounds; this is inferred from reading the module — likely accidental
  in a long-lived process but harmless in this single-token server).

## 3. Logging (`src/logger.js`)

None of this module's behavior is exercised by any test — no test file
imports `src/logger.js`.

- Every log line is prefixed with an ISO-8601 timestamp and a bracketed level
  tag (`[info]`, `[warn]`, `[error]`).
  [UNTESTED]
- The log message string is always passed through `redact()` before being
  written.
  [UNTESTED]
- An optional `meta` object is JSON-stringified and also passed through
  `redact()`; if `JSON.stringify` throws (e.g. circular reference), the literal
  string `'[unserializable meta]'` is logged instead of throwing.
  [UNTESTED]
- All log output is written to `process.stderr`, never `stdout`.
  [UNTESTED]

## 4. Sanitization (`src/sanitize.js`)

- `stripMarkup` removes HTML comments (`<!-- ... -->`) and HTML tags outright.
  [TESTED] `test/sanitize.test.js` — `'stripMarkup removes HTML tags and comments'`.
- `stripMarkup` decodes common HTML entities (`&lt;`, `&gt;`, `&amp;`, `&quot;`,
  `&#39;`/`&apos;`) and then re-neutralizes any resulting angle brackets — so
  entity-encoded markup (e.g. `&lt;script&gt;`) is decoded and then defanged
  rather than passed through as literal encoded text.
  [UNTESTED] — no test feeds entity-encoded input.
- `stripMarkup` replaces markdown link/image syntax `[text](url)` /
  `![alt](url)` with just the visible label text, discarding the URL target.
  [TESTED] `test/sanitize.test.js` — `'stripMarkup neutralizes markdown links and emphasis'`;
  also `test/mcp-e2e.test.js` — `'read tool output is framed and strips markup; token never leaks'`.
- `stripMarkup` replaces backtick and asterisk characters with spaces (defangs
  code spans and emphasis).
  [TESTED] `test/sanitize.test.js` — `'stripMarkup neutralizes markdown links and emphasis'`.
- `stripMarkup` also replaces `_`, `~`, `#`, `>`, and `|` characters with spaces
  (defangs underscores, strikethrough, headings, blockquotes, tables).
  [UNTESTED] — no test input exercises these specific characters.
- `stripMarkup` strips control characters (0x00–0x08, 0x0B–0x0C, 0x0E–0x1F,
  0x7F), preserving tab and newline.
  [UNTESTED]
- `stripMarkup` collapses runs of 2+ spaces/tabs into a single space, and runs
  of 3+ newlines into two.
  [UNTESTED]
- `stripMarkup` trims leading/trailing whitespace from its result.
  [UNTESTED]
- `safeField` returns `''` (unframed) for `undefined`, `null`, or `''` input.
  [TESTED] `test/sanitize.test.js` — `'safeField returns empty string for empty input (no framing)'`.
- `safeField` also returns `''` (unframed) if the input becomes empty *after*
  `stripMarkup` runs (e.g. input consisting only of markup/control characters).
  [UNTESTED] — no test supplies markup-only input to `safeField` directly.
- `safeField` neutralizes literal occurrences of the real fence markers
  (`FRAME_OPEN`/`FRAME_CLOSE`) found inside the value itself, replacing them
  with the plain-text strings `(UNTRUSTED)`/`(/UNTRUSTED)` before applying the
  real fence — preventing task content from forging a fence boundary.
  [TESTED] `test/sanitize.test.js` — `'safeField neutralizes a forged closing fence'`.
- `safeField` truncates content to `maxFieldChars` (default 2000) and appends
  `" …[truncated]"` inside the closing fence when truncation occurs.
  [TESTED] `test/sanitize.test.js` — `'safeField enforces the per-field character cap'`.
- `safeField` always wraps non-empty output exactly as
  `FRAME_OPEN + text + (truncation marker) + FRAME_CLOSE`.
  [TESTED] `test/sanitize.test.js` — `'safeField frames untrusted values in explicit delimiters'`.
- `capOutput` accepts either a raw string or an arbitrary object; objects are
  serialized via `JSON.stringify(payload, null, 2)`.
  [TESTED] (object-payload path only) `test/sanitize.test.js` — `'capOutput truncates oversized payloads with a notice'`.
  The raw-string-payload branch is [UNTESTED] by any test, and is not
  exercised by production code either — every current call site
  (`src/tools/read.js`) always passes an object.
- `capOutput` truncates to the cap and appends a notice stating the cap value
  and suggesting the caller narrow the request.
  [TESTED] `test/sanitize.test.js` — `'capOutput truncates oversized payloads with a notice'`.
- `capOutput` defaults to a 50000-character cap when `maxOutputChars` is
  nullish.
  [UNTESTED] — no test omits the second argument.
- `UNTRUSTED_NOTICE` is a fixed string (containing the literal `FRAME_OPEN`/
  `FRAME_CLOSE` glyphs as part of its explanatory text) that is prepended to
  **every** read-tool response regardless of whether that particular response
  actually contains any framed field.
  [UNTESTED] as to its exact text; its presence is asserted only indirectly —
  `test/mcp-e2e.test.js` checks that response text `includes(FRAME_OPEN)` /
  `includes(FRAME_CLOSE)`, which could in principle be satisfied by the
  notice's own text alone rather than by an actual framed field in the payload.

  [UNTESTED]
- `shapeSection.order` falls back to `s.order` if `s.section_order` is absent.

## 6. HTTP client (`src/client.js`)

- `API_BASE` is hardcoded to `https://api.todoist.com/api/v1`; no config or
  tool input can change it.
  [implicit — exercised throughout `test/client.test.js`]
- `assertAllowedUrl` throws `SsrfError` for a malformed URL string.
  [TESTED] `test/client.test.js` — `'SSRF allowlist accepts only https api.todoist.com'`.
- `assertAllowedUrl` throws `SsrfError` for any non-`https:` protocol
  (including `file://`).
  [TESTED] `test/client.test.js` — `'SSRF allowlist accepts only https api.todoist.com'`.
- `assertAllowedUrl` throws `SsrfError` for any hostname other than exactly
  `api.todoist.com`, including subdomain-suffix spoofing
  (`api.todoist.com.evil.example`) and the bare apex domain (`todoist.com`).
  [TESTED] `test/client.test.js` — `'SSRF allowlist accepts only https api.todoist.com'`.
- The SSRF check (`assertAllowedUrl`) is invoked inside `request()` on every
  fully-composed URL, but since `API_BASE` is fixed and every call site in
  `src/tools/read.js`/`write.js` passes a hardcoded path literal, no currently
  reachable code path can actually trigger it to throw in production —
  coverage of the throwing branches exists only via direct unit tests of
  `assertAllowedUrl`, not through `request()`.
  [UNTESTED as exercised through `request()`]
- The real API token is sent in the `Authorization: Bearer <token>` header on
  every request.
  [TESTED] `test/mcp-e2e.test.js` — `'read tool output is framed and strips markup; token never leaks'`
  (asserts `opts.headers.Authorization.includes(TOKEN)`).
- `request()` omits any query parameter whose value is `undefined`, `null`, or
  `''`, rather than sending it as an empty parameter.
  [UNTESTED]
- `request()` sets `Content-Type: application/json` and serializes `body` to
  JSON only when `body !== undefined`; GET-style calls with no body send no
  `Content-Type` header at all.
  [UNTESTED]
- `request()` logs `"<METHOD> <path>"` via `logger.info` before sending,
  deliberately excluding the `Authorization` header and query values from the
  log line.
  [UNTESTED]
- A network-level failure of `fetch()` itself (e.g. DNS/connection error) is
  wrapped into a `TodoistApiError` with a redacted message and no `status`
  property set.
  [UNTESTED]
- A non-2xx response is turned into a `TodoistApiError` carrying `res.status`
  and a message combining method, path, and the redacted response body text
  truncated to 500 characters; a failure to read the response body text itself
  is silently swallowed (`detail` stays `''`).
  [TESTED, partially] `test/client.test.js` — `'API error text never leaks the token'` —
  this test only asserts `err.status === 401`; per its own comment it does
  **not** verify that the error message text actually has the token redacted
  end-to-end through this path.
- A `204` response short-circuits to `null` without attempting to read/parse
  a body.
  [UNTESTED]
- An empty-string response body (any status other than 204) also short-circuits
  to `null`.
  [UNTESTED]
- If the response body is non-empty but fails `JSON.parse`, `request()` returns
  the raw text string rather than throwing.
  [UNTESTED]
- `getPaginated` requests pages of `min(200, cap - itemsSoFar)` and follows
  `next_cursor` until either the cursor is exhausted or the cap is reached.
  [TESTED] `test/client.test.js` — `'getPaginated follows next_cursor until exhausted'`,
  `'getPaginated respects the item cap'`.
- If an endpoint returns a bare array instead of the `{results, next_cursor}`
  envelope, `getPaginated` treats it as one final page and stops following
  cursors (no further pagination is attempted even if more data might exist).
  [UNTESTED] — no mock returns a bare array.
- `getPaginated`'s `truncated` flag is `true` only when the accumulated item
  count has reached the cap **and** a `next_cursor` is still present; an
  account whose data exactly equals the cap with no further cursor is reported
  as `truncated: false`. This distinction is not directly asserted by any test
  (`'getPaginated respects the item cap'` checks item count only, not the
  `truncated` value).
  [UNTESTED]
- The final item array is always sliced to exactly `cap` length even if the
  last page fetched pushed the running total over it.
  [TESTED] `test/client.test.js` — `'getPaginated respects the item cap'`.
- `getPaginated` defaults its `maxItems` argument to `config.maxItems` when
  omitted by the caller.
  [TESTED] `test/client.test.js` — `'getPaginated follows next_cursor until exhausted'`
  (called without a `maxItems` argument; relies on `cfg.maxItems = 200`).

## 7. Server lifecycle and registration (`src/index.js`, `src/server.js`)

- `createServer` registers the API key as a redaction secret
  (`registerSecret(cfg.apiKey)`) as its first action, before constructing the
  `McpServer` or the HTTP client.
  [UNTESTED] — no test asserts this ordering specifically (tests that rely on
  redaction re-register the secret manually).
- Read tools are registered in every mode, regardless of `cfg.readOnly`.
  [TESTED] `test/registration.test.js` — `'read-only mode registers only the 7 read tools, no writes'`,
  `'read/write mode registers the full 16-tool set'`; `test/mcp-e2e.test.js` —
  `'client sees exactly the read tools in read-only mode'`.
- Write tools' registration function (`registerWriteTools`) is only invoked
  when `cfg.readOnly` is falsy; in read-only mode those 9 tool names are
  entirely absent from the server (not merely hidden/disabled).
  [TESTED] `test/registration.test.js` — `'read-only mode registers only the 7 read tools, no writes'`;
  `test/mcp-e2e.test.js` — `'client sees write tools only in read/write mode'`.
- A fixed list of tool names (delete/reorder/assignment/workspace-analytics/
  reminder/filter tools) is never registered in either mode.
  [TESTED] `test/registration.test.js` — `'forbidden tools are never registered in either mode'`.
- `createServer` logs a single summary line at construction time stating the
  mode (`READ-ONLY` vs `READ/WRITE`) and the counts of read/write tools
  registered.
  [UNTESTED] — no test captures/inspects log output from `createServer`.
- `createServer` returns `{server, toolNames, readNames, writeNames}`, where
  `toolNames` is the concatenation of `readNames` then `writeNames`.
  [TESTED] `test/registration.test.js`.
- The MCP server identity is always reported as name `'todoist-mcp'`, version
  `'1.0.0'`, regardless of configuration.
  [UNTESTED]
- On config-load failure, `index.js` writes a redacted fatal message to
  `stderr` and exits the process with code 1, without ever writing to `stdout`.
  [UNTESTED] — no test runs `index.js` as a subprocess or checks its exit
  behavior/streams.
- Any other startup/runtime error caught by the top-level `main().catch`
  handler has its `stack` (or `String(err)` if no stack) redacted, written to
  `stderr`, then exits with code 1.
  [UNTESTED]
- On successful startup, logs `'Todoist MCP server listening on stdio.'` with
  the full list of registered tool names as metadata.
  [UNTESTED]

## 8. Read tools (`src/tools/read.js`)

- Every read tool's handler is wrapped in try/catch; a thrown error becomes
  `{isError: true, content: [{type:'text', text: 'Error: ' + err.message}]}`
  rather than crashing the server or the transport.
  [UNTESTED] — no test triggers a read-tool error path and inspects the result
  shape.
- `err.message` is emitted into that `isError` response as-is, without being
  passed through `redact()` at this point. The inline comment at
  read.js:36-37 asserts the message is "already redacted at the client layer,"
  but that only holds for errors that originate in `client.js` (e.g.
  `TodoistApiError`); any error thrown directly by a read tool's own handler
  code (e.g. `find-tasks-by-date`'s `'Provide either preset or date.'`, or a
  validation throw in `find-comments`) is not itself redacted anywhere before
  reaching this response.
  [UNTESTED]
- `find-tasks`: when a non-empty `query` is supplied, the tool always calls
  `/tasks/filter` and silently ignores `project_id`/`section_id`/`label`/
  `parent_id`/`ids` — they are not combined with the filter query nor is their
  presence-with-query flagged as an error.
  [UNTESTED]
- `find-tasks`: when no `query` is given, `ids` (an array) is joined with `,`
  into a single comma-separated query parameter.
  [UNTESTED]
- `find-tasks-by-date`: `preset` takes priority over `date`/`comparison` — if
  both are supplied, `date`/`comparison` are silently ignored with no error.
  [UNTESTED]
- `find-tasks-by-date`: throws `'Provide either preset or date.'` (becomes an
  `isError` tool result) if neither is supplied; this is enforced in the
  handler, not by the Zod schema.
  [UNTESTED]
- `find-tasks-by-date`: the `comparison` field is declared as
  `z.enum([...]).default('on').optional()`. Because `.optional()` is chained
  *after* `.default(...)`, an omitted field is short-circuited to `undefined`
  by the optional wrapper before the schema-level default can apply — the
  actual fallback to `'on'` is supplied entirely by the handler's
  `a.comparison ?? 'on'`, making the schema-level `.default('on')` unreachable
  dead configuration for the omitted-field case.
  [UNTESTED] — this tool is never invoked by any test.
- `find-comments`: throws if neither `task_id` nor `project_id` is given, and
  throws if both are given — an exactly-one-of constraint enforced at runtime
  in the handler rather than via Zod.
  [UNTESTED]
- `get-overview`: fetches projects, sections, labels, and tasks concurrently
  via `Promise.all`; a rejection from any single one of the four requests
  fails the entire overview call (no partial results are ever returned).
  [UNTESTED]
- `get-overview`: "due today" / "overdue" counts are computed by string-
  comparing each task's `due.date` against `new Date().toISOString().slice(0,10)`
  — i.e. always UTC "today" as measured on the server host, not any
  user-local timezone.
  [UNTESTED] (also runtime-dependent — see final section)
- `get-overview`: each of the four sub-fetches is independently capped at
  `cfg.maxItems`; the tool's input schema is empty, so a caller cannot request
  a higher or lower limit for this aggregate view specifically (unlike the
  other list tools, which accept a `limit` argument).
  [UNTESTED]
- `get-overview`: a section whose `project_id` doesn't match any project
  returned in the same call is still added to the internal `sectionsByProject`
  map but never appears in the output, since the output only reads sections
  keyed by project ids present in `projRes.items` — such an "orphaned" section
  is silently dropped, not surfaced as an error or a note.
  [UNTESTED]
- `get-overview`: the `labels` field in the output is a bare array of
  (framed) names — label ids are not included, so an agent cannot use this
  output alone to reference a label by id.
  [UNTESTED]
- `readResult` (used by all read tools) always prepends `UNTRUSTED_NOTICE` to
  the response text, even for tool calls whose payload happens to contain no
  framed field.
  [UNTESTED]

## 9. Write tools (`src/tools/write.js`)

No write tool is ever invoked (`callTool`) in any test; all entries below are
[UNTESTED] except where noted otherwise.

- Every write tool's handler uses the same generic try/catch → `isError`
  response pattern as read tools.
  [UNTESTED]
- As in read.js, `err.message` is emitted into the `isError` response without
  being passed through `redact()` at this point. write.js has no analogous
  inline comment claiming upstream redaction, but the same caveat applies:
  this only holds for errors that originate in `client.js`; a runtime throw
  from a write tool's own handler code (e.g. `add-comments`'s "Each comment
  needs task_id or project_id.") is not redacted anywhere before reaching this
  response.
  [UNTESTED]
- `write.js` never imports `src/sanitize.js`. Write tool responses
  (`writeResult`) are raw `JSON.stringify` of API-echoed fields (e.g.
  `created.content`, `created.name`, `updated.content`) with **no**
  `stripMarkup`/framing applied — unlike every read tool response.
  `add-tasks` and `update-tasks` differ in whose content this can be:
  `add-tasks` echoes back `content` the caller authored in the same call
  (`created.content` from the `POST /tasks` response), whereas `update-tasks`
  echoes `content` read from the Todoist API response to `POST /tasks/{id}`
  (`updated?.content` at write.js:124) — since that endpoint is a partial
  update whose response returns the task's full current state, `content` here
  reflects whatever the task's content currently is, including a value
  authored by anyone else with write access to the task (e.g. via another
  client), not necessarily anything sent in the caller's `update-tasks` call.
  [UNTESTED]
- Write tool responses are not passed through `capOutput` at all — there is no
  flood/size cap analogous to the read path's `maxOutputChars`.
  [UNTESTED]
- `add-tasks` issues one `POST /tasks` per task **sequentially** (an `await`
  inside a `for` loop), so N tasks in one call means N sequential round trips,
  not a batch/concurrent request.
  [UNTESTED]
- `add-tasks` result only echoes back `id`, `content`, and `url` per created
  task; other fields the Todoist API returned (assigned `project_id`,
  `priority`, `due`, etc.) are discarded from the tool response.
  [UNTESTED]
- `update-tasks` sends every field of the input object except `id` as the
  request body — there is no protection against a caller accidentally
  clearing a field by omission vs. explicit empty value, since Zod strips only
  genuinely `undefined` optional keys.
  [UNTESTED]
- `update-tasks` reports `ok: true` for every processed id purely because the
  request didn't throw — it does not verify the API's response reflects the
  intended change beyond a non-error HTTP status.
  [UNTESTED]
- `reschedule-tasks` requires at least one of `due_string`/`due_date`/
  `due_datetime` per task via a Zod `.refine()` — this validation happens at
  MCP input-parsing time (schema level), in contrast to the structurally
  similar "at least one of" requirements in `find-comments` and `add-comments`,
  which are enforced by a runtime `throw` inside the handler body. The two
  mechanisms differ in when/how the failure surfaces to the caller.
  [UNTESTED]
- `add-comments` enforces "exactly one of `task_id`/`project_id`" via a runtime
  throw **inside the per-comment loop**. If a batch contains multiple comments
  and a later one violates the constraint, any earlier comments in the same
  call have already been POSTed to Todoist with no rollback — the thrown error
  aborts the tool call but does not undo prior side effects, and the response
  gives no indication of which comments (if any) succeeded before the failure.
  [UNTESTED]
- `add-tasks`, `update-tasks`, and `reschedule-tasks` share the same
  partial-completion-on-error characteristic as `add-comments`: if the Nth
  item's HTTP request throws (e.g. a transient 5xx or a bad id), items
  `1..N-1` in the same call have already been created/mutated with no
  rollback, and the tool's `isError` response contains only the generic error
  text — not a breakdown of which items succeeded.
  [UNTESTED]
- Deletion, reordering, assignment, reminders, and filters are never
  implemented as tools in either mode (confirmed exhaustively against a
  forbidden-name list).
  [TESTED] `test/registration.test.js` — `'forbidden tools are never registered in either mode'`.

## Behaviors I could not determine by reading

- **Real Todoist API response shapes.** All pagination/response-envelope
  assumptions (`{results, next_cursor}` vs. a bare array, exact error body
  format, exact field names like `is_completed` vs `checked`) are inferred
  from the code's defensive handling, not confirmed against the live API.
  Whether the bare-array fallback path in `getPaginated` is ever actually hit
  in production depends on Todoist's real behavior per endpoint.
- **`get-overview`'s "today" boundary** depends on the wall-clock date (UTC)
  of the host machine at the moment the tool is called — its practical
  correctness for a user in a non-UTC timezone near midnight is a runtime
  condition, not something fixed by the code.
- **Node's built-in `fetch` error shapes.** `request()`'s network-error
  handling formats `err.message` from whatever `fetch()` throws; the exact
  shape of that error (and thus the exact text surfaced to the caller) depends
  on the Node.js version and underlying network condition at runtime.
- **MCP SDK behavior on schema validation failure.** Whether a Zod `.refine()`
  violation (e.g. in `reschedule-tasks`) surfaces as a protocol-level error or
  as a normal `isError` tool result is determined by
  `@modelcontextprotocol/sdk`'s internal handling, not by code in this repo.
- **File permission enforcement for `TODOIST_API_KEY_FILE`.** Comments in
  `config.js` describe the file as expected to be `0600`/claudecode-owned, but
  no code in this repo checks or enforces file permissions — actual exposure
  risk depends on how the deployment environment sets up that file.
- **`JSON.stringify` failure in `write.js`.** `writeResult` calls
  `JSON.stringify(payload, null, 2)` with no try/catch (unlike `logger.js`,
  which guards the equivalent call). Whether this can actually throw at
  runtime depends on whether the Todoist API ever returns a value that
  produces a circular structure or a `BigInt` in the echoed fields — not
  determinable from this code alone.
- **Concurrency/partial-failure interleaving in `get-overview`'s
  `Promise.all`** under real network latency or a mid-flight rate limit from
  Todoist is a runtime condition, not something the code's structure alone
  determines.
